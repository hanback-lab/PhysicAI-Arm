# Preparation

이번 장에서는 ROS 2에서 데이터를 수집하고, 이를 LeRobot 학습 데이터셋으로 변환한 뒤, 학습된 policy를 실제 로봇에서 실행하기 위한 준비 과정을 진행합니다. 학습은 직접 만든 데이터셋을 이용해 LeRobot으로 진행합니다. 노드를 작성할 때 노드 이름과 파일 이름을 맞춰 두면 혼동을 줄일 수 있습니다.

실습에는 총 3개의 노드가 필요합니다.

- `logger_node.py`: 에피소드별 원시 데이터 저장
- `parsing_node.py`: 원시 데이터를 LeRobot 데이터셋으로 변환
- `inference_node.py`: 학습된 policy를 이용한 실시간 추론 및 제어

학습은 별도 ROS 2 노드가 아니라 LeRobot의 `lerobot-train` 명령으로 진행합니다. 모든 실습은 workspace(`/home/soda/physicai_arm_ws`)에서 진행합니다. 다른 경로에서 진행할 경우, 코드마다 경로를 변경해야 합니다.

## logger_node

해당 노드를 실행하면 학습에 필요한 데이터를 저장하기 위해 에피소드별로 **학습 데이터를 수집**합니다. 노드를 실행하면 첫 에피소드 기록이 자동으로 시작됩니다. 기록을 마친 뒤 성공이면 's', 실패면 'f'를 입력합니다. 다음 에피소드는 'start'로 시작하고, 'q'를 입력하면 종료합니다.

**[logger_node 코드](/etc/logger_node.py)**

코드에서 `save_dir` 파라미터의 기본값 `<raw_dir>`(원시 데이터를 저장할 폴더)과 `task_name` 파라미터의 기본값 `<task_name>`은 해당 상황에 맞게 변경하여 작성해야 합니다. 코드를 직접 수정하지 않고 실행할 때 `ros2 run physicai_arm logger_node --ros-args -p save_dir:=dataset_raw -p task_name:=pick_red_token`처럼 지정할 수도 있습니다. `save_dir`를 상대 경로로 지정하면 노드를 실행한 위치(workspace) 기준으로 폴더가 만들어집니다.

이번 장에서는 저장 폴더(`save_dir`)를 `dataset_raw`, task name(`task_name`)을 `pick_red_token`으로 사용합니다.

또한 `logger_node`는 `/ee_pose` 토픽도 함께 구독해 states.csv에 EE 자세를 기록합니다. 이 값은 순기구학 노드(`fk_calc`)가 발행하므로, `fk_calc`를 실행하지 않으면 EE 위치·자세 열(`ee_x`~`ee_qz`)은 0, `ee_qw`는 1(회전 없음)로 채워집니다. 다만 `parsing_node`는 학습에 관절 값(`joint_0`~`joint_5`)만 사용하므로 이 장의 학습 자체에는 영향이 없습니다.

**코드 설명**

해당 코드는 ROS 2에서 실행되는 로그 수집 노드입니다. 로봇이 작업을 수행하는 동안 카메라 이미지, 로봇의 현재 관절 상태, 목표 관절 값을 받아서 하나의 에피소드 단위로 저장합니다.

기본 코드대로 할 경우 에피소드는 하나당 90초까지 기록 가능합니다. 시간 제한을 두어 노드를 종료하지 못하는 상황에서 자동 종료로 용량 초과를 방지합니다. LoggerNode 클래스는 Node를 상속받아 ROS 2 노드로 실행됩니다.

에피소드는 000001부터 시작하며 다음에 다시 시작할 때에는 `save_dir`을 같게 설정하면 마지막으로 끝났던 에피소드 다음 번호로 이어서 저장합니다. `episode_id` 파라미터에 1 이상의 값을 지정하면 해당 번호부터 저장합니다(기본값 0은 자동 번호). 에피소드 저장이 완료되면 해당 에피소드에서 저장한 front/top 이미지 프레임 수와 states/actions CSV 행 수를 출력하고, 현재 에피소드가 끝났음을 알려 줍니다.

이후 `setup_episode_directory()` 함수가 호출되어 에피소드 저장 폴더를 만듭니다. 각 에피소드는 'episode_000001'과 같은 이름으로 저장되고, images/front, images/top과 같은 폴더에 카메라 이미지를 저장합니다. 또한 관절 상태와 목표 관절 값을 저장하는 CSV 파일 (states.csv, actions.csv)을 생성하고, 에피소드 정보를 저장하는 json 파일 (metadata.json) 경로도 준비합니다.

저장할 데이터의 topic을 구독합니다. 카메라 이미지, 현재 관절 상태, 목표 관절 값, EE 자세(`/ee_pose`) 등의 정보를 받습니다. 이 코드는 별도의 타이머로 폴링하며 데이터를 모았다가 한꺼번에 저장하는 방식이 아닌, 각 topic의 콜백 함수가 호출되는 즉시 그 데이터를 파일에 저장하는 방식입니다. 즉 각 콜백이 자신이 받은 메시지를 바로 disk에 씁니다.

여기서 시각을 구하는 stamp_time() 함수가 핵심적인 역할을 합니다. 메시지 자체에 담긴 센서가 실제로 캡처한 시각이 있으면 그 값을 쓰고, 비어 있으면 now()로 대신합니다. 이렇게 각 스트림이 자신만의 정확한 시각을 갖도록 함으로써, 이미지, 상태, 행동이 서로 다른 시점의 데이터임에도 같은 시각으로 뭉뚱그려 저장되는 일을 방지합니다.

watchdog_cb() 함수는 60Hz로 주기적으로 실행되며, 현재 녹화 중인 에피소드가 90초를 넘기면 해당 에피소드를 자동으로 실패 처리하고 기록을 중단합니다.

- s : 현재 에피소드 성공 저장 (`success: true`)
- f : 현재 에피소드 실패 저장 (`success: false`, `fail_reason: "manual_fail"`)
- q : 프로그램 종료 (기록 중이었다면 `success: null`, `fail_reason: "quit"`으로 저장)
- start : 다음 에피소드 기록 시작 (현재 에피소드를 `s`/`f`로 끝낸 뒤에만 동작)

에피소드가 끝나면 finish_episode() 함수가 호출되어 에피소드 정보(task 이름, 시작·종료 시각, 성공 여부, 실패 사유, 프레임·행 수)를 metadata.json으로 저장하고 기록을 중지합니다. `parsing_node`는 `success`가 `false`인 에피소드만 제외하므로, 기록 중에 `q`로 종료해 `success: null`로 저장된 에피소드는 학습 데이터에 포함됩니다. 마지막 에피소드를 학습에서 빼고 싶다면 `f`를 입력한 뒤 `q`로 종료합니다. 마지막으로 메인 함수를 통해 노드를 실제로 실행합니다.


## parsing_node

`parsing_node`는 `logger_node`가 저장한 에피소드별 원시 데이터를 읽어 LeRobot이 학습에 사용할 수 있는 **LeRobot 데이터 형식으로 변환**합니다. 이 과정에서 실패한 에피소드는 제외하고, 타임스탬프를 기준으로 이미지, state, action을 매칭합니다.

<img src="pds/parsing_pipeline.png" style="width:60%;">

**[parsing_node 코드](/etc/parsing_node.py)**

코드에서 `RAW_ROOT`의 `<raw_dir>`(`logger_node`의 `save_dir`과 같은 폴더), `OUT_REPO_ID`의 `<id>/<dataset_name>`, `TASK_DEFAULT`의 `<task_name>`, 그리고 캘리브레이션 파일 경로인 `TOP_CALIB_PATH`/`FRONT_CALIB_PATH`(기본값 `./top_camera_calib.yaml`, `./front_camera_calib.yaml`)는 상황에 맞게 변경하여 작성해야 합니다. 이번 장에서는 `RAW_ROOT`를 `./dataset_raw`, `OUT_REPO_ID`를 `<id>/red_token_dataset`, `TASK_DEFAULT`를 `pick_red_token`으로 지정합니다. 캘리브레이션 파일은 [7-4. Camera Calibration](/Chapter07.%20AI%20Overview/7-4.%20Camera%20Calibration.md)에서 `calibration_node`로 생성한 top/front 카메라별 YAML 파일입니다.

> [!WARNING]
> `TOP_CALIB_PATH`/`FRONT_CALIB_PATH`에 지정한 경로에 파일이 없으면 `parsing_node`는 보정 없이 넘어가지 않고 `FileNotFoundError`로 종료됩니다. 캘리브레이션을 사용하지 않는다면 해당 값을 `None`으로 바꿉니다.

**코드 설명**

해당 코드는 로거 노드가 저장한 원본 에피소드 데이터를 실제 정책 학습에 쓸 수 있는 LeRobot 데이터셋 형식으로 변환하는 스크립트입니다. 이미지 파일, state/action csv를 시간축 기준으로 정렬, 매칭해서 하나의 프레임 시퀀스로 묶고, 최종적으로 Hugging Face Hub에 업로드까지 수행합니다.

`RAW_ROOT`는 로거가 저장한 원본 데이터 폴더 경로이고, `OUT_REPO_ID`는 변환 결과가 저장될 Hugging Face 데이터셋 이름입니다. `FPS`(20)는 데이터셋의 프레임 레이트이고, `IMAGE_SIZE`/`TOP_SIZE`는 front/top 이미지를 줄일 크기로 둘 다 가로 224, 세로 168입니다. `MAX_TIME_DIFF`(0.03초)는 서로 다른 스트림을 매칭할 때 허용하는 최대 오차로 이보다 차이가 크면 해당 프레임은 버려집니다. `TASK_DEFAULT`는 metadata.json의 `task_name`이 비어 있거나 `"classify"`일 때 대신 사용할 task 이름입니다.

`TOP_CALIB_PATH`/`FRONT_CALIB_PATH`는 Camera Calibration 실습에서 저장한 top/front 카메라의 캘리브레이션 결과(YAML) 파일 경로입니다. `main()` 시작 시 `load_undistorter()`가 각 파일을 읽어 `Undistorter` 객체를 만듭니다. `Undistorter`는 YAML의 `image_width`/`image_height`, `distortion_model`, `camera_matrix`(K), `distortion_coefficients`(D), `projection_matrix`(P)를 읽고, `distortion_model`이 `equidistant`면 fisheye 모델로, `plumb_bob`이면 일반(pinhole) 모델로 왜곡을 보정합니다. 실제 이미지 해상도가 캘리브레이션 해상도와 다르면 K와 P를 해상도 비율만큼 조정해 사용하며, 이때 가로세로 비율이 다르면 오류가 발생합니다. 왜곡 보정 맵은 해상도별로 최초 1회만 계산해 재사용합니다. 경로를 `None`으로 두면 해당 카메라는 보정 없이 파싱합니다.

보정은 `load_image()`에서 이미지를 224x168로 줄이기 전, 원본 해상도 단계에서 적용됩니다. top 캘리브레이션이 로드되면 첫 에피소드의 첫 top 이미지로 보정 전/후를 나란히 붙인 미리보기를 `./top_preview.png`로 저장하므로, 보정이 제대로 되었는지 파싱 전에 확인할 수 있습니다. 학습 데이터에 캘리브레이션을 적용했다면 추론(`inference_node`)에도 **반드시 같은 파일**을 지정해야 학습-추론 간 입력 분포가 어긋나지 않습니다.

`load_top_image()`는 resize한 top 이미지에서 `TOP_MASK` 영역(세로 0~94, 가로 0~69 픽셀)을 회색(128)으로 칠합니다. 데이터셋 태그 `leader_masked`에서 알 수 있듯이 top 카메라에 함께 찍히는 영역을 가려 policy가 학습에 불필요한 부분을 보지 않도록 하기 위한 처리입니다.

`nearest_by_time()` 함수가 이 스크립트의 핵심 매칭 로직입니다. 기준 시각(target_time)이 주어지면, 정렬된 데이터 리스트에서 그 시각과 가장 가까운 항목을 찾아 반환합니다. start_index를 넘겨받아 그 지점부터 앞으로만 탐색하기 때문에 효율적입니다.

`main()` 함수가 실제 변환을 수행하는 부분입니다. 먼저 `RAW_ROOT`가 있는지, 출력 폴더(`~/.cache/huggingface/lerobot/<OUT_REPO_ID>`)가 이미 있는지 확인합니다. 출력 폴더가 이미 있으면 `FileExistsError`로 종료하므로, 다시 파싱할 때는 `OUT_REPO_ID`를 바꾸거나 기존 폴더를 옮겨야 합니다.

이후 `LeRobotDataset.create()`로 이미지(168x224x3)/state(6)/action(6)의 shape과 dtype을 정의한 features 딕셔너리를 넘겨 빈 데이터셋을 만듭니다. 그리고 `RAW_ROOT` 아래의 episode_* 폴더들을 순회합니다. metadata.json의 `success`가 `false`인 에피소드와 states.csv, actions.csv, 이미지 폴더 중 하나라도 없는 에피소드는 건너뜁니다. 나머지 에피소드는 states.csv를 기준(anchor)으로 각 상태 시각마다 top 이미지, front 이미지, action을 nearest_by_time()으로 각각 찾아 매칭합니다. 이 셋 중 하나라도 시간 오차가 `MAX_TIME_DIFF`를 넘거나 이미지 로드에 실패하면 그 프레임은 건너뛰고, 매칭에 성공한 프레임만 `dataset.add_frame()`으로 데이터셋에 추가한 뒤 에피소드 단위로 `dataset.save_episode()`를 호출합니다. state는 `joint_0`~`joint_5`, action은 `target_joint_0`~`target_joint_5` 열을 사용합니다.

모든 에피소드를 처리하면 유효 에피소드 수, 전체 프레임 수, 건너뛴 프레임 수, 로컬 저장 경로를 출력하고, `dataset.finalize()`로 데이터셋을 마무리한 뒤 `dataset.push_to_hub()`로 Hugging Face Hub에 **공개(public)** 데이터셋으로 업로드합니다. 업로드에 실패해도 로컬에 만든 데이터셋은 그대로 남습니다.


## inference_node

`inference_node`는 학습된 policy를 실제 로봇의 **센서 입력과 joint target 출력에 연결**하는 노드입니다. 현재 카메라 이미지와 joint 상태를 입력받아 다음 action을 예측하고, 이를 로봇 제어 명령으로 publish합니다. 학습만 해서는 로봇이 움직이지 않습니다. 학습 결과인 policy를 실제 센서 입력에 연결해서 실시간으로 추론하고 제어하는 런타임 노드가 필요합니다.

training과 비슷해 보일 수 있지만, training은 dataset을 입력으로 받아 모델을 학습하고 그 결과로 weight를 만들어 냅니다. 이와 달리 inference는 실시간 센서 데이터를 입력받아 그때그때 추론하고 제어 명령을 출력합니다.

<img src="pds/training_inference.png" style="width:80%;">

LeRobot은 학습할 때 **정규화와 역정규화**를 이용합니다. 로봇 학습 데이터는 관측값과 행동값의 스케일이 극단적으로 다릅니다. 이 값들을 그대로 신경망에 넣으면 gradient 불균형, 학습 불안정이 생깁니다. 정규화는 이를 일정한 범위로 맞춰주는 작업입니다. 학습에서 정규화+역정규화를 한 뒤, 추론에서는 하지 않는다면 정규화된 공간이 아니므로 **입력 분포가 불일치**하여 성능이 저하됩니다. 따라서 추론 노드에 정규화와 역정규화 과정을 추가합니다.

추론에 사용될 observation의 형태와 action의 의미는 학습 때 사용한 형태와 의미를 일치시켜야 합니다. 이를 다르게 입력하면 로봇이 움직이지 않거나 엉뚱한 방향으로 움직이는 등 제대로 된 추론을 할 수 없게 됩니다.

**[inference_node 코드](/etc/inference_node.py)**

코드에서 `policy_path` 파라미터의 기본값 `<id>/<policy_name>`과 캘리브레이션 파일 경로 `TOP_CALIB_PATH`/`FRONT_CALIB_PATH`는 상황에 맞게 변경해야 합니다. `<id>/<policy_name>`은 자신이 학습해 업로드한 정책의 Hugging Face 저장소 경로(또는 로컬 경로)로 바꾸고, `TOP_CALIB_PATH`/`FRONT_CALIB_PATH`(기본값 `./top_camera_calib.yaml`, `./front_camera_calib.yaml`)는 `parsing_node`와 기본값이 같으므로, 파싱 때 경로를 바꿨다면 여기서도 동일한 파일을 가리키도록 맞춥니다. 기본값은 상대 경로이므로 노드를 실행한 위치(workspace) 기준으로 파일을 찾습니다.

`parsing_node`와 달리 `inference_node`는 캘리브레이션 파일이 없거나 읽을 수 없으면 경고만 출력하고 **보정 없이 계속 동작**합니다. 학습 데이터에 캘리브레이션을 적용했다면 실행 로그에 `[top] Loaded calibration`, `[front] Loaded calibration`이 출력되는지 꼭 확인합니다.

**코드 설명**

해당 코드는 학습된 ACT policy를 실제 로봇에 연결하는 ROS 2 런타임 노드입니다. `InferenceNode` 클래스가 카메라 이미지와 관절 상태를 구독해 다음 action을 예측하고 `/follower/joint_targets`로 발행합니다.

`__init__`에서 파라미터를 읽습니다. 각 값은 `--ros-args -p <이름>:=<값>`으로 실행할 때 바꿀 수 있습니다.

|파라미터|기본값|의미|
|---|---|---|
|`policy_path`|`<id>/<policy_name>`|불러올 정책의 Hub 저장소 또는 로컬 경로|
|`device`|`cuda`|`cuda`/`mps`/`cpu` 중 하나, 지정한 가속기를 쓸 수 없으면 자동으로 CPU로 전환|
|`fps`|`20.0`|추론 주기(Hz)|
|`max_age_s`|`0.5`|센서 데이터가 이보다 오래되면(초) 추론하지 않음|
|`top_calib_path`|`./top_camera_calib.yaml`|top 카메라 캘리브레이션 YAML 경로|
|`front_calib_path`|`./front_camera_calib.yaml`|front 카메라 캘리브레이션 YAML 경로|
|`command_deadband_rad`|`0.0`|이보다 작은 변화는 이전 명령값 유지 (0이면 사용 안 함)|
|`show_images`|`true`|debug 창(`ACT debug`) 표시 여부|

`ACTPolicy.from_pretrained()`로 정책 가중치를, `make_pre_post_processors()`로 전처리기(preprocessor)와 후처리기(postprocessor)를 함께 불러옵니다. 이 전/후처리기가 앞서 설명한 **정규화·역정규화**를 담당하며, 학습 때 저장된 통계를 그대로 사용하므로 추론 입력이 학습과 같은 분포에 놓입니다.

`_load_calibration()`은 `top_calib_path`/`front_calib_path`의 YAML 파일을 카메라별로 읽어 `parsing_node`와 같은 `Undistorter`를 만들고, **없거나 형식이 잘못됐으면** 경고를 출력한 뒤 해당 카메라는 보정 없이 진행합니다. 보정은 `_preprocess_image()`에서 이미지를 224x168로 줄이기 전에 `_undistort_image()`로 적용되며, 이후 RGB로 변환하고 0~1 범위의 float로 바꿉니다. 왜곡 보정 맵은 해상도별로 한 번만 계산합니다.

관절 상태는 `JointState` 메시지의 `name`을 보고 `ARM_JOINTS` 순서(`shoulder_pan`, `shoulder_lift`, `elbow_flex`, `wrist_flex`, `wrist_roll`, `gripper`)로 다시 정렬해 사용합니다. 메시지에 없는 관절이 있으면 오류를 출력하고 추론하지 않습니다.

이미지 콜백은 들어온 프레임을 전처리해 최신 이미지로 보관만 하고, 실제 추론은 `fps` 주기의 `control_loop()`에서 수행합니다. `_snapshot()`은 top/front 이미지와 관절 값이 모두 도착했는지, 그리고 세 스트림 모두 수신 시각 기준 `max_age_s` 이내로 최신인지 확인합니다. 하나라도 없으면 `Waiting for sensor data...`를 출력하며 대기하고, 오래됐으면 `Stale sensor data.`를 출력하고 그 주기를 건너뜁니다.

추론은 `_busy` 플래그로 중복 실행을 막은 뒤 별도 스레드(`_run_inference()`)에서 실행합니다. 배치를 만들어 preprocessor → `policy.select_action()` → postprocessor 순으로 통과시키고, 결과 action이 6개 값이고 모두 유효한 숫자인지 검증합니다. `command_deadband_rad`를 0보다 크게 설정하면 변화가 그보다 작은 관절은 이전 명령값을 유지해 미세한 떨림을 줄일 수 있습니다(기본값 0에서는 사용하지 않음). 최종 action은 `ARM_JOINTS` 순서의 `JointState`로 `/follower/joint_targets`에 발행되며, 10스텝마다 현재 관절 값(measured)과 명령값(target)을 로그로 출력합니다.

`_show_debug()`는 0.2초마다 debug 화면을 만들어 `/inference/debug` 토픽으로 발행하고, `show_images`가 `true`이고 디스플레이가 있으면 `ACT debug` 창으로도 보여 줍니다. 화면에는 모델에 실제로 들어가는 top/front 이미지(왜곡 보정 후), 관절별 측정값·명령값·차이, 입력 데이터의 최신 여부(`INPUT FRESH`/`INPUT STALE / MISSING`)와 마지막 명령 이후 경과 시간이 표시됩니다. 이미지 위의 빨간/초록 박스는 색상으로 찾은 토큰 후보를 표시한 것일 뿐 ACT가 선택한 목표가 아닙니다. 마우스로 영역(ROI)을 드래그하면 그 영역 안에서만 후보를 표시하고, 우클릭하면 ROI가 초기화됩니다. 이 표시는 화면용이며 모델 입력에는 영향을 주지 않습니다. 디스플레이가 없는 환경에서는 `rqt_image_view` 등으로 `/inference/debug` 토픽을 확인합니다.

`/inference/reset` 서비스를 호출하면 ACT의 action queue와 스텝 카운터가 초기화되어, 로봇을 처음 자세로 되돌린 뒤 새로운 시도를 시작할 수 있습니다.

## replay_node

수집한 데이터의 관절각이 알맞게 들어갔는지 replay 노드를 통해 확인할 수 있습니다. replay 노드는 수집했던 데이터를 다시 재생하는 노드입니다.

```python
import rclpy
from rclpy.node import Node
from sensor_msgs.msg import JointState
import pandas as pd
import time
import sys


JOINT_NAMES = [
    "shoulder_pan",
    "shoulder_lift",
    "elbow_flex",
    "wrist_flex",
    "wrist_roll",
    "gripper",
]


class EpisodeReplayNode(Node):
    def __init__(self, csv_path):
        super().__init__("replay_node")

        self.pub = self.create_publisher(
            JointState,
            "/follower/joint_targets",
            10
        )

        self.df = pd.read_csv(csv_path)
        self.get_logger().info(f"Loaded {len(self.df)} frames from {csv_path}")

    def replay(self):
        for i in range(len(self.df)):
            row = self.df.iloc[i]

            msg = JointState()
            msg.header.stamp = self.get_clock().now().to_msg()
            msg.name = JOINT_NAMES
            msg.position = [
                float(row["target_joint_0"]),
                float(row["target_joint_1"]),
                float(row["target_joint_2"]),
                float(row["target_joint_3"]),
                float(row["target_joint_4"]),
                float(row["target_joint_5"]),
            ]

            self.pub.publish(msg)

            if i < len(self.df) - 1:
                dt = float(self.df.iloc[i + 1]["timestamp"] - row["timestamp"])
                time.sleep(max(0.001, dt))

        self.get_logger().info("Replay finished")


def main():
    rclpy.init()

    if len(sys.argv) < 2:
        print("Usage: python3 replay_node.py <actions.csv>")
        return

    node = EpisodeReplayNode(sys.argv[1])

    time.sleep(1.0)
    node.replay()

    node.destroy_node()
    rclpy.shutdown()


if __name__ == "__main__":
    main()
```

```sh
ros2 run physicai_arm replay_node \
dataset_raw/episode_000001/actions.csv
```

**코드 설명**

해당 코드는 저장된 파일을 읽어 로봇의 움직임을 다시 재생하며 확인하는 노드입니다. 로봇을 직접 조종해서 기록했던 목표 관절 값을 토대로 topic으로 발행하여 로봇이 그대로 따라하도록 합니다.

실행 명령어를 통해 원하는 에피소드의 관절 값을 재생할 수 있습니다. `rclpy.init()` 함수로 ROS 2를 초기화하고 CSV 파일 경로가 입력되었는지 확인합니다. 경로가 없으면 사용 방법을 출력하고, 정상적으로 입력되었다면 `EpisodeReplayNode` 객체를 생성하여 관절 값을 차례로 발행합니다.

실행할 때는 재생하려는 에피소드의 `actions.csv` 경로를 인자로 적어 주면 됩니다. 위 예시는 `episode_000001`을 재생하므로, 다른 에피소드를 보려면 경로의 번호만 변경하면 됩니다. 데이터를 수집한 후, replay를 통해 데이터의 품질을 검증할 수 있습니다.

`setup.py`에 해당 노드를 추가하고 build를 해야 한다는 것을 잊지 마시기 바랍니다.
